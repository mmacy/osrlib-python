# Phase 12 plan — terminal modes

Implementation plan for phase 12 of [the osrlib spec](spec.md): `SessionMode.VICTORY` with its command-legality rules, and non-battle party wipes routing to `GAME_OVER` — the terminal-state machinery opened once for both changes. Victory becomes *reachable* in phase 15, when completing a concluding quest transitions into it; this phase ships the mode, its legality contract, and the shared wipe machinery that phase 15's transition will stand beside. Phase 12 is order-independent of phase 13 and must land before phase 15. The milestone: **a trap or deprivation wipe ends the session in game-over, and mode-legality tests hold for victory.**

Five facts shape the design:

- **The legality machinery is already data, so the victory half of the phase is almost entirely one enum member plus tests.** Every play command declares an explicit `allowed_modes` frozenset that cannot contain a value that does not exist, and every referee command inherits `_ALL_MODES = frozenset(SessionMode)`, computed at import from the enum itself — so adding `VICTORY` makes play commands illegal and referee commands legal in it by construction, with no dispatch changes. Persistence restores the mode by enum value (`SessionMode(str(payload["mode"]))`) and `PlayerView.mode` is a plain string, so both carry the new value untouched. A new serialized enum value is the additive case the spec's versioning rules name explicitly: no `schema_version` bump, no migration, and an older engine failing to load a `victory` save is the documented accepted risk.
- **Game-over is escapable by design, and victory must not be — the one command where the two terminal modes differ.** The sessions guide is explicit that referee commands run in `game_over` because "a referee correcting the world doesn't stop just because the party fell", and the escape is load-bearing machinery, not an oversight: `PlaceParty(town)` flips a wiped session to `town`, where `PurchaseHealing(service="raise_dead")` — a real, implemented temple service with `DeathRecord` tracking the revival window — brings the party back. Victory has nothing to salvage, and the spec forecloses the equivalent: post-victory play is out of scope by decision, and its stated rationale — "a post-victory mode can arrive additively later where shipping 'continue' first and tightening later could not" — decides the tension in the spec's own words. `PlaceParty` is the only referee command whose effect is a mode transition into play, so it alone distinguishes the terminal modes: legal in `game_over` (the salvage door, unchanged), illegal in `victory` (`_ALL_MODES` minus `VICTORY`, a `wrong_mode` rejection). Every other referee command — grants, awards, flags, spawns, time, dice — is legal in both, which is also what lets phase 15's rewards land after the transition, exactly as the spec requires.
- **The salvage flow forces the wipe check to be edge-triggered.** The naive rule — after any command, no living members means game-over — would flip the salvaged session straight back: `PlaceParty(town)` executed from `game_over` leaves zero living members, and a level-triggered check would re-enter `game_over` before the temple could act, deadlocking the documented revival flow. The wipe check therefore fires only when the command's own events contain a `DeathEvent` targeting a party member — the exact walk `_record_deaths` already performs in `execute()` — and the party is then without living members. A wipe is an edge (someone just died); a dead party being ferried to the temple is a state, and states don't re-trigger.
- **The defeat transition gets one home.** Battle's `_check_ends` currently owns the only wipe routing: it flips the mode and emits `GameOverEvent(reason="the party has fallen")` itself. Moving both into the session-level check makes every wipe — battle, trap, deprivation, poison in town — one code path with one reason string, and it is event-stream-neutral: all five `_check_ends` call sites (two in `start_battle`, three in the resolve-round handler) place the returned end events in tail position and return, so a centrally appended `GameOverEvent` lands immediately after `BattleEndedEvent(code="battle.ended.defeat")`, byte-identical to today's stream. No stored golden contains a TPK, so no golden regenerates.
- **A wipe mid-command must not leave the rest of the handler playing with corpses.** Handlers keep running after a death resolves: a chute trap that kills the whole party still relocates the bodies and runs the arrival checks, which would discover treasure, spring further traps, open a keyed encounter, and accrue movement — and a deprivation wipe mid-`Rest` would keep advancing the span, wandering checks included. All of it is deterministic today, but it opens play state and consumes draws on behalf of the dead, and the centralized check would then have to unwind an encounter that should never have started. The engine already states the principle at `_room_trap_check`: "a trap needs a living victim: a party with no one left standing rolls no spring die at all." This phase extends that guard to every procedure that initiates new activity: entry checks, the wandering check, and the turn-advance loop. No existing golden reaches these paths (nothing in them wipes), so behavior is unchanged for every living party.

## Scope

In scope:

- `SessionMode.VICTORY`, a `terminal` property on the enum, and the legality census: play commands illegal in both terminal modes, referee commands legal in both, `PlaceParty` legal in `game_over` only
- The centralized, edge-triggered wipe check in `GameSession.execute`, and battle's defeat transition folding into it
- Wiped-party guards on the exploration procedures that would otherwise initiate new activity for a dead party
- The phase golden (a scripted trap wipe replaying and restoring clean), `tests/test_terminal_modes.py`, docs, and the changelog

Out of scope (deferred to the phase or track that picks each up):

- **The transition into victory** — phase 15: completing a concluding quest is the only entrance, `AdventureCompletedEvent` and the authored completion narrative ride it, and nothing in this phase constructs a path into the mode. Tests assign `session.mode = SessionMode.VICTORY` directly, the same direct-state posture the battle tests already use for hit points; shipping a transition surface nothing can call would be dead accommodation code.
- **Post-victory play** — out of scope by spec decision; this phase's `PlaceParty` exclusion is what keeps the door shut so a post-victory mode can arrive additively later.
- **Any change to `game_over` semantics** — the salvage flow (`PlaceParty(town)` → `raise_dead`) is documented, deliberate, and untouched; this phase adds the non-battle *entrances* to `game_over`, never touches its exits.
- **New rejection codes, events, or message templates** — none needed, pinned: `session.command.wrong_mode` already carries the mode value, `GameOverEvent` and its `session.game_over` template exist, and the reason string is unchanged. The docs drift gates see nothing new.
- **A `Ruleset` flag** — terminal-state routing is engine correctness, not an optional rule or adaptation; there is nothing to configure.
- **Death records, revival windows, and `raise_dead` mechanics** — consumed as-is by the salvage tests, modified nowhere.

## Work items

### 1. The mode and the legality census — `crawl/commands.py`

- `VICTORY = "victory"` joins `SessionMode`, wire value lowercase like its siblings. The enum docstring grows the terminal-modes note: `game_over` and `victory` end the session — play commands are illegal, referee commands remain legal, and neither mode is ever left by play (the referee salvage door out of `game_over` is `PlaceParty`, documented there).
- A `terminal` property on the enum — `self in (SessionMode.GAME_OVER, SessionMode.VICTORY)` — because "is the session over" is a question the wipe check, phase 15's transition, and any front end all ask; putting it on the enum gives it one home with no new module-level export. `_ALL_MODES` and `_FIELD_MODES` are import-time computations and need no edit.
- `PlaceParty.allowed_modes = _ALL_MODES - frozenset({SessionMode.VICTORY})` — the one carve-out, with the docstring carrying the rationale: a concluded adventure cannot be resumed (post-victory play arrives additively later or not at all), while `game_over` remains listed because teleporting the fallen party to town is the first step of the documented revival flow. Its `Modes:` list therefore names every mode but `victory`.
- The docstring sweep: every referee command that hand-lists its modes (`GrantItem`, `GrantCoins`, `AwardXP`, `SetFlag`, `SpawnMonsters`, `SpawnNpcParty`, `SetDoorState`, `AdvanceTime`, `RollDice`, `IdentifyItem`) gains `victory` in the list; play commands' lists are already exact and change nowhere.

### 2. The centralized wipe check — `crawl/session.py`

- In `execute()`, after the handler succeeds and immediately beside `_record_deaths` — before the event log extends and before listeners run: if the mode is not terminal, the command's events contain a `DeathEvent` whose `target_id` is a party member, and `party.living_members()` is now empty, then clear `battle` and `encounter`, set `mode = SessionMode.GAME_OVER`, and append `GameOverEvent(reason="the party has fallen")` to the command's events. One walk serves both bookkeeping steps — `_record_deaths` already identifies exactly the member-death events the trigger needs.
- Placement pins, each deliberate: before the log extend, so the event is in the log and in the `CommandResult` like any handler event; before listeners, so a quest tracker or narrator sees the session end in the same result; after the handler, so every death source — trap, falling, deprivation, poison tick, battle, and any future one — routes through a check that never needs to know it exists. A referee command that kills (an `AdvanceTime` that lets poison finish the last member, in town or anywhere else) wipes exactly like a play command, from any non-terminal mode.
- The terminal-mode skip is the victory-stickiness rule: a party that dies *after* victory (a referee advances time and a lingering poison resolves) stays in `victory` with no `GameOverEvent` — the session already concluded, and terminal modes never transition again. The same skip makes the check idempotent in `game_over`: further deaths among the already-fallen emit no second ending.
- The `NPC` boundary holds for free: `DeathEvent`s for monsters and NPC adventurers carry non-member ids and never trigger the walk's member test, exactly as `_record_deaths` treats them today.
- The reason string lives once, in the check — see the next item.

### 3. Battle's defeat transition folds in — `crawl/battle.py`

- `_check_ends`'s defeat branch keeps everything battle-specific — detecting the wipe, clearing `battle` and `encounter`, returning `[BattleEndedEvent(code="battle.ended.defeat")]` so every caller stops the round — and drops the mode flip and the `GameOverEvent`, which the session-level check now appends. The mode a caller observes after `execute()` returns is unchanged (`game_over`), and the event stream is unchanged: all five call sites tail-position the end events (verified in this plan's research: `start_battle` twice, the resolve-round handler's block loop, slow-attacks pass, and end-of-round pass all `return` or `break` immediately after extending), so the centrally appended event follows `BattleEndedEvent` exactly where the in-handler emission sat.
- This is the greenfield move, stated: two code paths that set `GAME_OVER` and construct the same event with the same prose would be the duplication `AGENTS.md` bans; the spec's "terminal-state machinery opened once for both changes" is an instruction to build it once.
- `test_tpk_sets_game_over` passes unchanged (it asserts the mode and the code's presence); no golden stores a TPK, so no regeneration.

### 4. Wiped-party guards — `crawl/exploration.py`, `crawl/session.py`

- The invariant, pinned: **once no member lives, no procedure initiates new activity within the same command** — no new encounter, no new discovery, no further cadence. Concretely: `_area_treasure_check` and `_keyed_encounter_check` gain the same head guard `_room_trap_check` already has (no living members, no procedure); `wandering_check` returns no-check when no member lives; and the per-turn loop in `GameSession.advance_turns` stops the span when the party has no living members — a deprivation wipe twenty turns into a night's rest truncates the span at the wipe, because the fatigue cadence, the wandering cadence, and the remaining rest all belong to the living. What already happened stands: relocation events for a chute that killed en route still emit (the state genuinely changed — the bodies are elsewhere), and effect expiries already elapsed are honest bookkeeping.
- The guards are behavior-invisible to every session that keeps a living member — every existing golden and test — because each guard's condition is reachable only after a wipe, and are what keeps the centralized check simple: it never has to unwind an encounter opened on behalf of the dead, and the event stream after the last death reads as an ending, not as corpses discovering treasure.
- Draw-sequence note for the record: on the wiped paths these guards *do* change which draws would have occurred after the wipe (no keyed-encounter spawns, no wandering roll), which is exactly the point — and no stored golden or fixture reaches a wiped state, so nothing regenerates.

### 5. Docs and spec impacts — applied with the implementation PR

- **`docs/spec.md` needs zero edits**: the "Victory and session end" section states this phase's contract in the present tense — victory as a terminal mode mirroring game-over, play commands illegal, referee commands legal, and the non-battle wipe gap closed — and the roadmap entry exists. The `PlaceParty` exclusion is a pinned interpretation of "the session concludes rather than continuing" recorded in this plan and the command docstring, below spec altitude.
- **`docs/adaptations.md` gains no entries**, stated deliberately: session modes have no SRD basis — B/X has no session, no terminal state, and no rule this phase reinterprets. The register's silence is the phase 10 and 11 precedent.
- **`docs/guides/sessions-commands-events.md`**: the "small, closed set" sentence and the mode-gating paragraph gain `victory`; the referee paragraph gains the one-command asymmetry (every referee command runs in both terminal modes except `PlaceParty`, which cannot resume a concluded adventure — and the existing "referee correcting the world" sentence stays, now explicitly the salvage door); the modes-form-a-loop paragraph gains the second terminal ending with a forward note that the transition into `victory` arrives with the authored-quest layer, plus the non-battle wipe sentence — a trap or starvation ends the session exactly as a lost battle does.
- **Docstrings**: `GameOverEvent`'s "(TPK)" parenthetical widens to any party wipe; `GameSession.execute` documents the wipe check among its bookkeeping; `advance_turns` documents the truncation rule.
- **`CHANGELOG.md`** `[Unreleased]`: an Added bullet for `SessionMode.VICTORY`, the `terminal` property, and the legality contract including the `PlaceParty` carve-out; a Fixed bullet for non-battle party wipes — previously a party that died to a trap, a fall, poison, or starvation left the session in `exploring` (or `town`, or `encounter`) forever, executing nothing but referee commands yet never ending; now every wipe routes to `game_over` with the same `GameOverEvent` a lost battle emits. No release work item — bullets ride `[Unreleased]` per the cadence.

### 6. Tests — `tests/test_terminal_modes.py` (new) and the phase golden

- **The legality census, restated completely rather than patched**: for every class in `ALL_COMMAND_CLASSES`, terminal-mode membership follows referee-ness — play commands' `allowed_modes` are disjoint from both terminal modes, referee commands contain both, `PlaceParty` alone contains `game_over` and not `victory`. The existing `test_referee_commands_are_legal_everywhere` restates around the carve-out, and its `REFEREE_COMMANDS` set gains the two members it silently omits today (`identify_item`, `spawn_npc_party`) so the census is total.
- **Victory legality at the executed seam**: with `session.mode = SessionMode.VICTORY` assigned directly, a play command sweep rejects `wrong_mode` (params carrying `"victory"`), the referee surface (`GrantItem`, `AwardXP`, `SetFlag`, `AdvanceTime`, `RollDice`) executes accepted, and `PlaceParty` rejects `wrong_mode`.
- **Victory stickiness**: in `victory`, a lingering poison finishing the whole party under a referee `AdvanceTime` leaves the mode `victory` and emits no `GameOverEvent` — the terminal skip pinned from the victory side.
- **Non-battle wipes, one per entrance**: a trap wipe (`MoveParty` onto a springing `kills` trap with `affects="party"`) ends in `game_over` with the `GameOverEvent` in tail position and `battle`/`encounter` cleared; a deprivation wipe (flag on, tracks pre-set to the damage threshold, members at 1 hp, `AdvanceTime` across the day boundary); an encounter-mode wipe (open encounter, poison resolving during a `Wait` round) with the encounter cleared; a town wipe (poison under `AdvanceTime` while in `town`). Each asserts the mode, the event, and — the edge-trigger pin — that a *subsequent* referee command among the corpses emits no second `GameOverEvent`.
- **The salvage flow, end to end**: TPK → `PlaceParty(town)` accepted with mode `town` and **no** re-triggered game-over (the level-vs-edge distinction made load-bearing) → `GrantCoins` → `PurchaseHealing(service="raise_dead")` revives → `EnterDungeon` accepted. The test is the regression fence around the edge-trigger design; a future "simplification" to a level-triggered check fails it immediately.
- **Guards**: a chute trap that kills the party mid-slide arrives without discovering the destination cache or opening its keyed encounter; a wiped party's span truncates in `advance_turns` (clock stops at the wipe turn, no wandering roll after); `wandering_check` consumed no draw for a dead party.
- **Persistence**: `save`/`load` round-trips both terminal modes; a loaded `victory` session still enforces its legality.
- **The golden** — `tests/generate_phase12_goldens.py`, `tests/goldens/phase12_wipe.json`, `tests/test_phase12_goldens.py`, on the phase 11 pattern (the test imports the generator's build/run). A small authored dungeon whose second cell carries a `kills=True, affects="party"` gas trap with no save; the seed is chosen so the 2-in-6 spring fires on entry, so the wipe is scripted, not lucky. The scripted run: enter, step, die — mode `game_over`, `GameOverEvent` last — then two accepted referee probes (`RollDice`, `SetFlag`) proving the terminal session still executes and logs referee commands. Replay of the accepted log reaches identical final state, and `load(save)` equals `replay(seed, commands)` — the standing equivalence guarantee now covering a session that *ends*, which no existing golden does.
- The full gate green: `uv sync && uv run ruff format --check && uv run ruff check && uv run pyright && uv run pytest && uv run mkdocs build --strict`.

- The milestone runs: the phase golden's trap wipe ends in `game_over` and replays and restores clean; a deprivation wipe test ends the same way; the victory legality census holds at both the declaration and the executed seam.
- One home for the defeat transition: `GameOverEvent` is constructed in exactly one place, battle and non-battle wipes emit the identical ending, and the battle TPK event stream is byte-identical to before the fold.

- No `SCHEMA_VERSION` bump, no migration, no new codes or events, and no existing golden regenerated — the only golden change is the new phase 12 file.
- The guide documents both terminal modes and the one-command asymmetry; no spec edit and no adaptations entry lands — both silences argued in this plan.
