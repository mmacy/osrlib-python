# Phase 11 plan — conditions, gates, and narrative blocks

Implementation plan for phase 11 of [the osrlib spec](spec.md): the condition union (`has_item` with consume-on-success, `flag_equals`, `effect_active`), an optional `requires` gate on door specs and level-placed transition specs with the gate-refusal rejection codes and the lock-composition rules, and the narrative-block model in its full three-audience shape, defined at first use and reused unchanged by later phases; `validate_adventure` grows condition item-id checks. This is the second link of the phase dependency chain 10 → 11 → 14 → 15: phase 10 built the item-identity surface (`has_item` consumes its id domain), and phases 14 and 15 reuse this phase's condition union and narrative block on triggers and quests. The milestone: **a golden scenario in which a key-gated door refuses with authored text while consuming no draws and no time, opens once any member carries the key, a toll transition consumes on success, a locked-and-gated door requires both, and a door set open by referee command admits passage until it closes.**

Five facts shape the design:

- **The gate slots into the exact seam where `locked` already sits, and open-door passage needs zero movement work.** The lock is checked as an opening barrier only in `_handle_open_door` and `_handle_force_door` (`exploration.py`; `_handle_pick_lock` reads it merely as its `not_locked` precondition); `_handle_move_party` tests only passability (`state.open`), so "a door standing open admits passage without a gate check" is the movement path's existing behavior, and `_swing_shut` closing party-opened doors is what makes "if the door closes again, the gate re-applies" fall out for free. `SetDoorState` already rewrites only the overlay and never reads the spec — the spec's "`SetDoorState` … never touches `requires`" is true before this phase writes a line.
- **The name `Condition` is taken.** `core/effects.py` exports `Condition`, the named-condition `StrEnum` (paralysed, petrified, dead, …), and `TrapEffect.condition` and `EffectDefinition.condition` already mean that enum. The phase's predicate union therefore ships as `ConditionSpec` in a new `crawl/gates.py`, never as a second `Condition`. Evaluation reads session state (party inventory, flags, the ledger), so the module is crawl-layer — but its evaluation helpers take core-typed inputs (`Sequence[Character]`, `Mapping[str, str | int | bool]`, `EffectsLedger`), so `gates.py` imports only `core` and stays importable by `dungeon.py` without a cycle.
- **The golden comparator is byte-for-byte, so the success beat is a planned golden regeneration.** The spec pins that success text rides the normal door and transition events as an optional authored beat, which means a new optional field on `DoorEvent` and `LocationEnteredEvent`. `test_phase4_goldens.py` compares `model_dump(mode="json")` output canonically, so every stored golden containing those events gains a `"narrative": null` key and must be regenerated — a mechanical, pure-additive diff, explained in the commit message per the standing golden rule. Loading older saves is unaffected (`extra="ignore"` plus the default), and no `SCHEMA_VERSION` bump: additive optional fields are the rule the version history already applies.
- **The player view masks gates by construction, not by new code.** `EdgeView` carries exactly `kind`, `door_open`, and `door_wedged` — it never carried `locked` or `stuck`, and it will never carry `requires` or a narrative block. The no-leak posture ("content wiring is the game's secret") is pinned by extending the leak test, not by writing masking code.
- **Rejections are log-invisible, which makes replay equality the purity proof.** A rejected command joins neither the command log nor the event log, so the golden's scripted run interleaves refusal probes between accepted commands while the replay executes accepted commands only — and the two reaching identical final state (streams, clock, inventory) *is* the proof that a gate refusal consumes no draws, no time, and no items. One pre-existing defect blocks the unconditional form of that proof: `DungeonState.door(ref)` is get-or-create, and every door handler touches it during validation, so a *refused* door command materializes a default overlay entry in serialized state today — a live violation of the spec's "mutates nothing" that also lets `doors` insertion order diverge between a probed run and its replay while `_swing_shut` iterates that dict on an event-emitting path. Work item 4 fixes the materialization; the proof then holds with no script constraints.

## Scope

In scope:

- `NarrativeBlock` in the new `crawl/narrative.py` — the three-audience model, full shape, all beats
- `ConditionSpec` (members `HasItemCondition`, `FlagEqualsCondition`, `EffectActiveCondition`), `GateSpec`, and the pure evaluation helpers in the new `crawl/gates.py`
- `requires: GateSpec | None` on `DoorSpec` and `TransitionSpec`; a `TrapEffect` validator forbidding `requires` on trap-effect transitions
- Gate checks in `OpenDoor`, `ForceDoor`, and `UseStairs` with the `exploration.door.gate_refused` and `exploration.transition.gate_refused` rejection codes carrying the authored refusal text
- The rejection-purity groundwork: door-state reads stop materializing overlay entries, so a refused door command mutates nothing — the pre-existing defect this phase's proof makes load-bearing
- Consume-on-success: the widened consumption primitive, the new `ItemConsumedEvent`, and `WedgeDoor`'s spike consumption joining it
- The success beat: `narrative` on `DoorEvent` and `LocationEnteredEvent`, the formatter appending it, and the golden regenerations that follow
- `validate_adventure` resolving `has_item` ids in door and transition gates against the effective equipment catalog plus the magic-item catalog
- The phase golden (`tests/goldens/phase11_gates.json`), `tests/test_gates.py`, docs, and the changelog

Out of scope (deferred to the phase or track that picks each up):

- **Triggers, quests, the journal, the interpreter, and the `source` field** — phases 13–15; this phase ships the vocabulary they consume and nothing that consumes it.
- **`SessionMode.VICTORY` and non-battle wipes to game-over** — phase 12.
- **The per-level ambient guidance slot** — phase 15, with the quest surface (`LevelSpec` has no prose field today, and it stays that way here).
- **Condition combinators (`all_of`/`any_of`)** — rejected for now, pinned: the union grows additively when a consumer demonstrates the need; the spec's vocabulary is three variants, and a door wanting lock-plus-gate already composes two layers by design.
- **Trap-bypass conditions and condition-keyed description variants** — spec-designed but spec-deferred, with their content-pack interaction; recorded so the silence reads as deliberate.
- **Coin-denominated tolls** — a consequence, pinned: `has_item` speaks catalog ids and coins are not items, so a gold toll is not expressible; authors mint a token item (the phase 10 bundled-item surface exists precisely for authored objects) and gate on that. A coin-condition variant arrives additively if a consumer demands it.
- **Gates on `EnterDungeon`, `TravelToTown`, or town services** — not gate sites by spec, which names door specs and level-placed transition specs only; a gated dungeon mouth is an authored gated door on level 1.
- **Gate sites in content packs** — zero pack work by construction: packs place no doors and no level transitions, and the one transition a pack can carry (inside a trap effect) cannot gate because the model validator rejects it at parse. `validate_content_pack` is correct unchanged.

## Work items

### 1. The narrative block — `crawl/narrative.py` (new)

- `NarrativeBlock`, frozen, all fields `str = ""` (the prose-field convention `AreaSpec.description` set): the display beats `refusal` and `success` (gates), `fired` (triggers), `offer`, `progress`, and `completion` (quests); the `journal` form; the LLM `guidance`, never displayed verbatim; and the `speaker` attribution, free prose by spec. Empty string means unauthored.
- The full shape ships now, quest and trigger beats included, on the spec's explicit instruction: the model is "defined at first use and reused unchanged by later phases" — an amended-per-phase block would be exactly the churn that sentence forbids. This is spec-mandated forward definition, not speculative scaffolding; the docstring names which beats which carrier reads so the unused-today fields are legible.
- Module docstring orients: narrative is authored content attached to mechanical objects; display beats are shown verbatim by deterministic renderers, guidance is trusted-as-content steering for LLM narrators (the description-prose posture), and visibility is the carrier's business — the block itself is inert data. `__all__ = ["NarrativeBlock"]`; imports nothing beyond pydantic.

### 2. The condition union and the gate — `crawl/gates.py` (new)

- Three frozen condition models discriminated on `condition_type`: `HasItemCondition` (`condition_type: Literal["has_item"]`, `item_id: str` min length 1, `consumes: bool = False`), `FlagEqualsCondition` (`"flag_equals"`, `key: str` min length 1, `value: str | int | bool` — the exact union `SetFlag` and `FlagSetEvent` already carry), `EffectActiveCondition` (`"effect_active"`, `kind: str` min length 1 — a free string because the effect-kind vocabulary is data-driven and open). `ConditionSpec` is the annotated discriminated union; the discriminator values are the spec's own names, wire-stable.
- `GateSpec`, frozen: `condition: ConditionSpec`, `narrative: NarrativeBlock | None = None`. The gate is the mechanical object that carries the narrative block, per the spec's "every mechanical object — quest, objective, gate, trigger — carries an optional narrative block"; hanging the block on the door instead would give ungated doors a meaningless narrative slot.
- `condition_holds(condition, *, members, flags, ledger) -> bool` — the single, pure evaluation entry point. Level-triggered by construction: it reads live state at call time and stores nothing. Per variant, pinned:
    - `has_item`: some member's carried inventory holds an instance with that catalog id — `Inventory.all_instances()` (pack, worn, shield, wielded, rings: carried is the whole test, equipped included), matching mundane instances on `template.id` and magic instances on `template_id` (the spec's "equipment or magic item"). Valuables never match — they are id-less by spec. `consumes` does not affect evaluation, which stays pure. **The matching rule itself lives in `core/items.py` as the additive public `Inventory.carried_item(item_id)`, not as a private helper here**: "does this pack hold item X" is an inventory question, and consumption (work item 6) asks the identical one — a private twin in `gates.py` would leave the toll and the gate free to disagree, which is exactly the divergence a `_find_item`-shaped helper already demonstrates. `condition_holds` and `first_holder` call it; so does `_consume_item`. A spent stack (quantity zero, expressible only on a magic instance) is not carrying, so anything the gate can find, the toll can take.
    - **The member domain is every party member, living or dead** — `party.members` in order. The spec says "some party member's carried inventory", dead members stay in the party (the party carries its dead and their packs), and a living-only reading would soft-lock the quest whose key rides a corpse. This deliberately differs from the actor-selection pins (trap victims, treasure recipients take the first *living* member): those pick who acts or suffers; a gate tests what the party possesses.
    - `flag_equals`: `flags.get(key)` compared strictly — equal value *and* matching boolness (`isinstance(stored, bool) == isinstance(value, bool)`), because Python's `True == 1` would otherwise make an authored int match a stored bool. An absent key equals nothing, `False` included: absent is absent, and authors who want a default set it with `SetFlag`.
    - `effect_active`: some member has an active effect of that kind — `ledger.active_on(member.id, kind)` per member, in member order. Location-attached effects never count: the spec says attached to a party member.
    - Determinism: every iteration walks lists in stored order (members, `all_instances()`, the ledger); no set is touched.
- `first_holder(members, item_id) -> Character | None` — the consumption target: the first member in marching order whose carried inventory matches, the same matching rule as evaluation, because both call `Inventory.carried_item`. Marching order is `Party.members` order, the established meaning.
- `__all__ = ["ConditionSpec", "HasItemCondition", "FlagEqualsCondition", "EffectActiveCondition", "GateSpec", "condition_holds", "first_holder"]` — no matching helper among them, since that surface belongs to `Inventory`. Imports: `core.character`, `core.effects`, `crawl.narrative` — no crawl import beyond `narrative`, so `dungeon.py` can import `GateSpec` cycle-free, and neither module is re-exported anywhere else (the public-surface test's re-export rule).

### 3. The `requires` fields — `crawl/dungeon.py`

- `DoorSpec.requires: GateSpec | None = None` and `TransitionSpec.requires: GateSpec | None = None`, docstrings stating the contract: the gate is a stateless authored predicate evaluated when opening the door or taking the transition is attempted; it is orthogonal to `locked` (a door carrying both requires both), `PickLock` addresses only the lock, `SetDoorState` rewrites only the overlay, and an open door admits passage unchecked.
- A `model_validator` on `TrapEffect` rejects a `transition` carrying `requires`: a trap-effect transition is a forced relocation, not something the party attempts, and never gates (spec). Pydantic enforcement at parse covers adventures and content packs alike with no second validation site. This narrows nothing previously expressible — `requires` did not exist, so no existing document can carry it — hence additive, no `SCHEMA_VERSION` bump (it stays 3), no migration.
- Saves embed the whole adventure, so the new fields serialize into every save with defaults; pre-phase saves load unchanged. `dungeon.py` imports `GateSpec` from `crawl.gates` and does **not** add it to `__all__` — one home per symbol.

### 4. Rejection-purity groundwork — `crawl/dungeon.py`, `crawl/exploration.py`

- The defect, named: `DungeonState.door(ref)` is get-or-create-and-store, and `_door_state`/`_known_door` call it from every door handler's validation phase — so a refused `OpenDoor` (locked, stuck, gated) and a blocked `MoveParty` beside a closed door each materialize a default `DoorState` entry in serialized state. That violates the spec's "a rejected command … mutates nothing", lets a save taken after a refusal diverge from its replay, and — because `_swing_shut` iterates `doors.items()` on an event-emitting path — can emit swing-shut events in probe order rather than accepted-command order. Pre-existing and unnoticed because `TestRejectionPurity` compares streams, clock, and logs, never full state; this phase's headline proof makes it load-bearing, so it is fixed outright, not pinned around.
- The fix: reads never store, and the released surface never moves. `DungeonState.door(ref)` keeps its documented get-or-create contract, its named test, and its mutate-through test uses untouched; what changes is the crawl-internal read path. `_door_state` (and `_known_door` atop it) becomes the non-storing read — `doors.get(ref)`, else a transient default carrying the `starts_open` seed it already applies — and every write point materializes explicitly at the moment it mutates, through one seeded materializer helper (the seed applies only when creating the entry — materializing an already-stored door never overwrites it, else a re-wedge would resurrect `starts_open`): open and force success, close, wedge, unlock, secret-door discovery (`_reveal`'s `discovered = True` — the write a first enumeration missed), and `SetDoorState`, which passes its explicitly addressed edge where the handlers pass the party-relative one — and which materializes only when it actually sets something, since a referee write with none of its four optional fields set changes nothing and must leave no entry behind. Routing `SetDoorState` through the seeded materializer also closes a latent wrinkle: today it materializes an unseeded entry, so a referee write touching a `starts_open` door first would store it shut. Validation reads answer identically (the transient default equals the stored default), `_swing_shut` iterates only genuinely operated — hence stored — doors, and the views already use `.get`.
- Consequences: new saves stop accumulating untouched-door entries; old saves load unchanged (redundant default entries are harmless data); the phase 4/5 goldens shed the entries their accepted logs only ever read, folded into the regeneration work item 7 already plans; replay determinism is untouched, since accepted commands materialize identically in both runs.
- Pinned by test: `TestRejectionPurity` extends to full-session-state equality across a rejection (the strongest form — a state dump compared before and after), plus the direct pins that a refused door command and a blocked move leave `dungeon_state.doors` keyless, a found secret door stays found (the discovery write materializes), and a referee write on an untouched `starts_open` door stores it open.

### 5. The gate checks — `crawl/exploration.py`

- One uniform rule, pinned: **the gate check is the last validation step** — after every mundane rejection, before any draw, mutation, time cost, or flag write. Concretely: `_handle_open_door` checks `no_door` → `already_open` → `locked` → `stuck` → gate; `_handle_force_door` checks its member/door/`not_stuck` census → gate → *then* sets the noise flag and rolls (a gate-refused forcing never happened: no noise, no surprise denial, no draw — rejection purity, stated in the docstring); `_handle_use_stairs` checks `stairs.none` → gate → then relocates and accrues movement. Rationale for mundane-before-gate: it preserves every existing rejection's order (ungated behavior is bit-identical), and it makes `gate_refused` fire exactly when the gate alone bars the way — the authored refusal is the final word, the dramatically honest beat, and on `ForceDoor` it is also the only order that keeps the refusal draw-free.
- The refusal: `Rejection(code="exploration.door.gate_refused", params={"direction": …, "refusal": …})` and `Rejection(code="exploration.transition.gate_refused", params={"refusal": …})` — literal codes (the docs scanner requires literals), the `refusal` param present only when the gate's narrative block carries a non-empty refusal beat (`Rejection.params` admits `str`; note it admits no `bool`, which nothing here needs). Distinct from `exploration.door.locked` by spec: distinct cause, distinct code.
- The unaffected census, each pinned by test: `CloseDoor`, `WedgeDoor`, and `ListenAtDoor` never evaluate gates (the gate guards opening, not touching); `PickLock` never evaluates gates and keeps rejecting `exploration.lock.not_locked` on a gated-but-unlocked door — a thief is not a universal quest bypass; `MoveParty` through an open gated door is unchecked (existing passability logic); `SetDoorState` evaluates nothing and its referee-visibility `DoorEvent` carries no beat.
- A shared helper keeps the three call sites identical without breaking the docs scanner, which raises on any non-literal `Rejection(code=...)`: `_gate_refusal(session, gate) -> str | None` evaluates `condition_holds` with `session.party.members`, `session.flags`, `session.ledger` and returns `None` on pass or the refusal beat (possibly empty) on failure; each call site then constructs its own `Rejection` with its literal code, adding the `refusal` param only when the returned text is non-empty.
- Time: gates add no entry to the time-cost census — a gated success costs exactly what the ungated command costs (zero for doors, the odometer's 30 units for stairs), and a refusal costs nothing.

### 6. Consumption — `crawl/exploration.py`, `crawl/events.py`, `messages.py`

- On a gated command's success with `consumes=True`: remove one instance of the item from the first holder in marching order (`first_holder`), then emit the new `ItemConsumedEvent` **before** the command's primary event — the toll is paid at the threshold, before the door event or the arrival cascade (relocation events, door traps, keyed encounters) lands. Consumption is an effect of the successful command, never of evaluation; the holder is resolved inside the same execution, so it cannot go missing between check and take.
- Consumption is per success, level-triggered, stateless, pinned: every successful execution of the gated command consumes again while the condition holds — a consumed key-door whose door swings shut wants another key; the non-consuming key-door reopens freely; nothing tracks "already consumed". One-time unlocks are phase 14 authoring (a trigger sets the door open or a flag).
- The primitive: widen `_consume_item` to the full carried surface — it looks the instance up through `Inventory.carried_item`, the same method a `has_item` gate evaluates by, and `_remove_instance` learns the `rings` slot it currently misses (which makes it behaviorally identical to `_remove_magic_instance`, so that twin collapses into it and its call sites move over — one home per symbol) — returning the consumed instance rather than today's bare `bool`, which is what lets the event stamp a magic consumption's `instance_id`. The find-then-consume pairs collapse onto the same lookup so that finding and taking cannot disagree: the wedge's spike-carrier search, the give path, and battle's item-use path each take first and read the returned instance. `_find_item` survives only as the mundane-item presence check whose subject is shipped gear by definition (a torch to light, tools to pick a lock with), and its docstring says why it is narrower. Its existing callers — provisions, ignite, the wedge, the give and drop paths — keep working unchanged (equipment and magic-item ids are disjoint namespaces, so the widened match cannot cross-resolve), pinned by a sweep test, and `WedgeDoor`'s spike consumption — silent today — now emits the same `ItemConsumedEvent`, closing the inconsistency while the phase-4 golden is regenerating anyway (work item 7); the alternative, a speaking gate-consumption next to a silent spike, would be two consumption surfaces.
- `ItemConsumedEvent` in `crawl/events.py`: `event_type: Literal["item_consumed"]`, `allowed_codes = {"exploration.item.consumed"}`, fields `character_id: str`, `item_id: str`, player visibility. The `item_id` follows the acquisition masking convention, pinned: a mundane consumption carries the catalog id; a magic consumption carries the instance's session-scoped `instance_id`, never the `template_id` — an unidentified talisman's true identity must not ride a player-visibility event, the doctrine `ItemAcquiredEvent` set in `_distribute_haul` and the leak test already asserts. Registered in `CRAWL_EVENT_CLASSES`/`ALL_EVENT_CLASSES`; `messages.py` gains its template.

### 7. Success beats on events — `crawl/events.py`, `messages.py`, the goldens

- `DoorEvent.narrative: str | None = None` and `LocationEnteredEvent.narrative: str | None = None`. Set only when a gated command succeeds and its gate's narrative block carries a non-empty success beat: on the `.opened`/`.forced` door event, and on the level-or-dungeon-crossing `LocationEnteredEvent` the transition's `_relocate` emits (threaded as an optional `_relocate` argument only `UseStairs` supplies; area-entry boundary events never carry it). The degenerate case, pinned: a level-placed transition whose destination is its own level is authorable and emits no crossing event, so its success beat has no carrier and is dropped — stated in the `TransitionSpec` docstring and the authoring guide (put beats where they display); validation stays out of it, since a beat with no stage is advisory territory, not a dangling reference.
- The no-baked-prose argument, stated in the field docstrings because this is the codebase's first authored-text-on-an-event: events still carry message codes and structured fields, and the beat is content data in a structured field — the spec's explicit carve-out ("authored text on an event is content data … not a violation"), the same trust posture as description prose. Engine-baked English remains banned.
- `format_message` appends a non-empty `narrative` field after the templated text, one generic total hook — the default English formatter is the library's deterministic renderer, so the beat displays verbatim and the golden transcript proves it.
- The golden consequence, planned: regenerate exactly the stored goldens whose event logs contain `DoorEvent` or `LocationEnteredEvent` (the phase 4 delve and phase 5 milestone goldens; the generators enumerate the rest by running). The diff is exactly two planned things — added `"narrative": null` keys and `WedgeDoor`'s new consumption event from work item 6 — explained in the commit message per the standing rule. The third change work item 4 produces, the shed untouched-door entries, has nowhere to appear in these files: neither golden stores dungeon state, so the shedding shows up only in the new phase golden, which records the door overlay explicitly. This is a behavior-visible additive change, not a version-stamp re-bless — the release-time prohibition is untouched.

### 8. Validation — `crawl/adventure.py`

- `validate_adventure` (signature unchanged, consumer-pinned) walks every level's door edges and level-placed transitions; for each `requires` whose condition is `has_item`, the `item_id` resolves against the effective equipment catalog (base ∪ bundled, the existing `_effective_equipment` product) **or** the shipped magic-item catalog — the union `has_item` itself matches. Error lines follow the house shape, one per reference, into the single accumulated list: `"dungeon {id} level {n}: door {edge_key} gate references unknown item {item_id!r}"` and the transition twin naming its position.
- `flag_equals` keys and `effect_active` kinds get no checks, pinned by spec: flag writers and effect vocabularies are open domains, and advisory analysis (a flag nothing sets, a kind nothing attaches) is authoring-tool territory, not engine validation.
- Trap-effect transitions need no gate check here — the `TrapEffect` validator already made a gated one unrepresentable. The pre-existing gap that trap-effect transition *destinations* go unvalidated is real but out of scope: it predates this phase, gates don't touch it, and widening destination validation belongs to its own fix; recorded here so it isn't read as overlooked.

### 9. Views and visibility — pinned by test, not built

- `EdgeView` already exposes exactly `kind`, `door_open`, `door_wedged` — no spec fields, so `requires`, conditions, and narrative blocks (guidance included) never reach the player view by construction. The leak test extends to assert the serialized player view contains no `requires`, `condition_type`, `guidance`, or `refusal` keys. The referee view continues to carry the full adventure — wiring is referee-visible by design.
- The refusal text and success beat are player-visible where they land (the rejection returned to the caller; the player-visibility events) — authored text is for players, wiring is not, exactly the spec's visibility split.

### 11. Tests — `tests/test_gates.py` (new) and the phase golden

- **Evaluation units**: each variant true and false; magic-item matching by `template_id`; equipped and ring-slot items counting as carried; valuables never matching; a spent stack not counting; the dead member's pack counting (the domain pin); strict flag equality (`1` vs `True` both directions, absent key vs `False`); location-attached effects not counting; `first_holder` marching-order selection; purity (no state change across evaluation). `Inventory.carried_item` carries its own unit tests beside the other inventory methods, and the dead-member domain is pinned **at the command seam as well** — a corpse's key opening a door, a corpse's token paying a door's and a transition's toll — because a unit test on `condition_holds` alone cannot catch a handler that narrows the domain to the living.
