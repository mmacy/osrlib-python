# Phase 10 plan — adventure-bundled items

Implementation plan for phase 10 of [the osrlib spec](spec.md): an `Adventure` document carries its own item templates — the same weapon, armour, gear, and ammunition models the equipment catalog ships, discriminated on the `item_type` field they already carry — and the engine resolves them everywhere it resolves authored item ids, under the same contract as phase 9's bundled monsters: colliding ids rejected at validation, never overridden. This is the item-identity surface for authored objects — the quest key and the temple idol the gates/triggers/quests section builds on — and the first link of the phase dependency chain 10 → 11 → 14 → 15. The milestone: **a bundled gear item placed in a treasure cache is taken, granted, and observed by catalog id, and a colliding id is rejected at validation.** "Observed" here means the acquisition surfaces report the bundled id — `ItemAcquiredEvent.item_ids` and the inventory views carry it exactly as they carry shipped ids; the condition-side observation (`has_item`) is phase 11's, consuming the id domain this phase establishes. Unlike phase 9, the spec already states this phase's contract in full (the adventure-model bullet added with the gates/triggers/quests section), so the roadmap needs no new entry and the spec impact is one clarifying sentence (work item 4).

Four facts shape the design:

- **`ItemInstance` embeds its full template, so downstream of acquisition nothing changes by construction.** Equip legality, encumbrance, combat, give-and-drop bookkeeping, persistence, and replay read the embedded template, never the catalog. Drop piles store bare ids (`DroppedItem.item_id`), but resolution back to a template happens only at take time inside `_distribute_haul`, which has the session in scope — so a bundled item dropped, saved, loaded, and retaken round-trips with no persistence work. No golden embeds a serialized `Adventure`, so the additive field re-blesses nothing.
- **Every crawl site that resolves an authored item id has the session in scope; every other `load_equipment()` site resolves ids a bundled id cannot reach.** The authored-id sites are three: `_handle_grant_item` (`session.py`), `_distribute_haul` (the one resolution behind cache takes, drop-pile recovery, and battle-drop recovery — piles store bare `DroppedItem.item_id`s resolved only at take time), and `_handle_purchase_equipment` (the deliberate carve-out, work item 3). The `GiveItems` recipient path (`_grant_mundane`) resolves the catalog today but never needs to — the giver provably carries the instance, and work item 3 passes its embedded template through instead, deleting the site. The remaining crawl lookups cannot see a bundled id: `ignite`'s `"torch"`/`"lantern"` lookups sit behind the handler's fixed-id whitelist, and the player view's armour-masking lookup (`views.py`) resolves magic-item `base_item_id`s — shipped by construction, since adventures bundle no magic items and the only runtime `base_item_id` assignment rolls off a shipped table. The `core` sites — magic-item `base_item_id` resolution in AC, encumbrance, and weapon-material code, NPC-party gear, treasure weights — are shipped-by-construction the same way, and `create_character`'s purchase loop, whose ids are caller-supplied rather than shipped, runs pre-session where no adventure exists and layering (`core` never imports `crawl`) keeps it that way — a bundled id passed there raises the base catalog's bare `ValueError`, an authoring fact the guide's items section states (work item 4). No core site needs the session.
- **The consumer contract is already pinned on both surfaces.** `validate_adventure` keeps its `(adventure, monsters, equipment)` signature with `equipment` remaining the *base* catalog, unioned internally — osr-forge's existing call is correct unchanged, exactly as phase 9 arranged for monsters. And `validate_content_pack` is correct unchanged too: the spec pins that content-pack features reference the shipped catalog only, so the pack gate keeps resolving items against the base catalog, and the spec's "pack insertion validates item references against the target adventure's effective catalog" lands with zero pack-side code — insertion is consumer-side (an editor writes entries into areas), and validating the inserted result *is* `validate_adventure`, which now resolves the union.
- **Shipped equipment and magic-item ids are disjoint namespaces today — verified, not assumed — and the collision rule keeps them one identity space.** The spec's "the catalog [is] the single item-identity namespace" and phase 11's `has_item` (which matches "equipment or magic item" by one id) both require that an item id name exactly one thing per session. So bundled ids must collide with neither the equipment catalog, nor the magic-item catalog, nor each other — all three checked in one helper. (`treasure_weights` ids are deliberately outside the rule: that list already shares `"staff"` with the weapons list, proof it is an encumbrance table, not item identity.)

## Scope

In scope:

- `Adventure.items: tuple[ItemTemplate, ...] = ()` — bundled item templates carried by the document, `ItemTemplate` being the existing exported discriminated union
- The effective catalog: base `load_equipment()` ∪ `adventure.items`, held by `GameSession` as `effective_equipment` — the exact name phase 9 reserved for this seam — resolving at every authored-id engine site
- The town-shop pin: `PurchaseEquipment` keeps resolving the shipped catalog — argued in work item 3 — with the new `items.purchase.not_stocked` rejection code as its honest refusal for a bundled id
- `validate_adventure` bundled checks: intra-bundle uniqueness, equipment-catalog and magic-catalog collision, cache `item_ids` against the union
- Docs and spec impacts: the one-sentence town-shop clarification, the id-domain docstring sweep, the authoring guide's items section, the changelog bullet

Out of scope (deferred to the phase or track that picks each up):

- **A runtime content-registration API** — rejected, pinned: the phase 6 boundary stands unmoved through its second document-carried phase; content arrives as document data, never live registration.
- **Bundled magic items** — deferred until a consumer demonstrates the need, the same evidence bar monsters and items each cleared. Magic-item identity is a different contract (instantiation rolls charges, contents, and sentience on the treasure stream at take time), and authored *placement* of shipped magic items already works via `FeatureSpec.magic_item_ids`. Until then, adventures bundle no magic items, which is itself load-bearing: it is why every `base_item_id` site — in `core`'s AC, encumbrance, and weapon-material code *and* in `crawl/views.py`'s armour-masking display lookup — stays shipped-by-construction; that is the site list a future magic-bundling phase must revisit.
- **Catalog shadowing or override semantics** — rejected, pinned, mirroring phase 9: a collision is a validation error, never an override. Silently re-statting `torch` would change light sources, ignite consumption, and every cache that names it; an adventure that wants a variant names a variant id.
- **A pack-side item bundle (`ContentPack.items`)** — rejected, spec-pinned: bundled item ids are adventure-scoped by construction, and a pack carrying its own item ids would embed dangling references into arbitrary target adventures. A pack cut from an adventure whose cache names a bundled id reports `pack.feature.unknown_item` — the designed dangling-is-legal posture, recorded here so nobody reads it as a gap.
- **A purchasable-custom-stock surface (a `TownSpec` stock list)** — deferred until a consumer demonstrates the need; the default this phase pins is that bundled items are not purchasable at all.
- **Bundled items in generated treasure** — the treasure tables and stocking procedure reference shipped construction by design, exactly as phase 9 left band tables shipped-only; authored placement is the cache.
- **Conditions and trigger consequences over item ids** — phases 11 and 14 consume this phase's id domain; the spec's "item ids in conditions" validation lands with the conditions themselves. The headline consumer is phase 15's fetch quest: the example TUI's idol is today an id-less `ValuableSpec` in a cache, and phase 15 converts it to a bundled gear item placed by `item_ids` so its objective can match on the idol's catalog id — the conversion this phase's surface exists to make possible.

## Work items

### 1. The field — `crawl/adventure.py`

- `Adventure.items: tuple[ItemTemplate, ...] = ()`, docstring naming the contract: bundled templates join the shipped equipment catalog for this adventure's sessions everywhere the engine resolves authored item ids (caches, grants, drop-pile recovery) and ride every carry surface (gives, equips, drops) through their embedded templates; ids must not collide with the equipment catalog, the magic-item catalog, or each other; the empty tuple is the universal default. `ItemTemplate` imports from `core.items` beside the imports already there — crawl → core, the permitted direction.
- The schema consequence, pinned: additive and defaulted — every existing save and document loads unchanged with the default applied, no `SCHEMA_VERSION` bump (it stays 3), no migration entry, nothing re-blessed. Pydantic parses the discriminated union from documents on the `item_type` each template already serializes.
- No `__all__` change anywhere: the field is a class attribute, and `ItemTemplate` is already exported from `osrlib.core.items`.

### 2. The helper and validation — `crawl/adventure.py`

- `_effective_equipment(adventure, base) -> tuple[EquipmentCatalog, tuple[str, ...]]`, the sibling of `_effective_monsters` beside it: always returns a usable catalog plus every skipped colliding id, so both callers get a total answer. The seen-set seeds from the base catalog's ids across all four lists *plus* the shipped magic-item ids (`load_magic_items()` — the module already imports it); accepted templates append to their `item_type`'s list in document order; `treasure_weights` passes through untouched. Collisions filter *before* construction — `EquipmentCatalog`'s own uniqueness validator raises a bare `ValueError`, the wrong failure shape for content problems. An empty bundle returns `(base, ())` — the base catalog object itself, the `@cache`d singleton: no copy, no behavior change for every adventure that bundles nothing.
- `validate_adventure` keeps its exact signature; `equipment` remains the *base* catalog. It calls `_effective_equipment` beside `_effective_monsters` and folds each colliding id into the one accumulated error list — "bundled item id {id!r} collides with the catalog", one line per id, phase 9's message shape, "the catalog" meaning the whole item-identity namespace — through the standard "adventure validation failed" gate. `_validate_feature` takes the effective catalog for `item_ids` (its `magic_item_ids` check keeps the shipped magic catalog), so a cache naming a bundled id validates and the failure path stays total: a colliding id resolves to its first occurrence and the report names the root cause without a spurious "unknown item" echo per reference.
- `replay_game` re-validates by construction (it rebuilds through `GameSession.new`); `load_game` continues to trust saved content, with work item 3's `__init__` construction as its typed backstop.

### 3. The session and the redirects — `crawl/session.py`, `crawl/exploration.py`

- `GameSession.__init__` builds the union beside the monster one — `_effective_equipment(adventure, load_equipment())`, raising `ContentValidationError` naming the colliding ids when the helper reports any (the doctored-save backstop: a save carrying a colliding bundle fails typed at restore, not with a bare `ValueError` at first take) — stores it as `self._equipment_catalog`, and exposes the read-only `effective_equipment` property, docstring mirroring `effective_monsters`.
- The redirects, each one line: `_handle_grant_item`'s `load_equipment().get(command.item_id)` → `session.effective_equipment.get(...)`; `_distribute_haul`'s `equipment = load_equipment()` → `session.effective_equipment`, covering cache takes, drop-pile recovery, and battle-drop recovery at once. The `GiveItems` path is a deletion, not a redirect: `_apply_give` captures `_find_item(giver, item_id).template` before `_consume_item` runs, and `_grant_mundane` takes that template instead of an id — the giver provably carries the instance (`_validate_carried` has already passed), so re-resolving a catalog could only ever hand over a re-lookup that differs from the object the giver held. Today a bundled item handed over would crash on `_grant_mundane`'s unguarded `load_equipment().get` — a latent defect the deletion closes before it is reachable.
- `ignite`'s `"torch"`/`"lantern"` lookups stay on `load_equipment()`, pinned: the handler whitelists `("torch", "lantern", "oil_flask")` before any lookup runs, so no bundled id can reach those sites, and redirecting them would dress engine-fixed-id lookups as authored-id surfaces — churn buying nothing, since the views' shipped-by-construction display lookup keeps "no bare `load_equipment()` in crawl" false regardless.
- **The town-shop pin — the phase's one deliberate carve-out.** `_handle_purchase_equipment` keeps resolving `load_equipment()`, with a one-line comment stating the constraint: the town shop stocks the shipped equipment lists; bundled items enter play through caches and grants. Rationale, pinned: the spec's town offers "the equipment lists" — the SRD's commodity lists, which is also the fiction (a shop sells commodities; purchase *materializes* a fresh instance, and the idol in room 12's cache must not have a second copy on a shelf); and phase 15's fetch quest completes on `has_item` matching the idol's catalog id, so a purchasable bundled item would let the party buy the quest closed for its required-field `cost_gp`. The spec's "everywhere the engine resolves item ids" reads as the authored-content surfaces its own sentence enumerates — caches, grants, observation — exactly as phase 9's "everywhere" left the shipped band tables shipped-only. An author who wants purchasable custom stock is the deferred `TownSpec` surface in scope-out.
- The carve-out refuses honestly: on a base-catalog miss the handler checks `session.effective_equipment` and rejects a bundled id with the new `items.purchase.not_stocked` code (params naming the item), falling back to `session.command.unknown_item` for a genuinely unknown id — the spec's own distinct-cause-distinct-code posture (phase 11 separates `gate_refused` from `locked` on the same principle), so a front end never tells a player that an id sitting in the party's own pack is unknown. Both codes land in `PurchaseEquipment`'s docstring, and both are pinned by test.

### 4. Docs and spec impacts — applied with the implementation PR

- **`docs/spec.md` § The adventure model**, the bundled-items bullet: one added sentence — the town's shop stocks the shipped equipment lists only; bundled items enter play through caches and grants. Everything else the phase does is already in the spec's present tense; no roadmap edit (entry 10 exists).
- **The id-domain docstring sweep**: `FeatureSpec`'s "`item_ids` (any id from `load_equipment`…)" gains the effective domain; `GrantItem`'s `unknown_item` rejection line names it; `EquipItem`'s "the catalog id (from `load_equipment`…) for a mundane one" does too — a bundled item equips by an id no index documents; `PurchaseEquipment` states the shipped-only stock rule and both rejection codes; `Adventure`'s docstring covers both bundle fields; `validate_adventure`'s `equipment` Args line mirrors the `monsters` line (the *base* catalog, unioned internally); `validate_content_pack`'s `equipment` Args line and the module docstring's closure paragraph each gain one sentence making the deliberate silence legible — packs carry no item bundle and reference the shipped catalog only, by spec — so the pack gate's base-catalog resolution reads as the pin it is, not an oversight.
- **`docs/guides/authoring-custom-content.md`** retitles to "Authoring custom classes, spells, monsters, and items" (nav label follows) and gains the items section: building each template kind with `model_validate`, bundling via `Adventure.items`, the three-way collision rule, placement in caches and grants, the not-purchasable rule, the warning that `create_character`'s `purchases` resolve the shipped catalog only (pre-session, a bundled id raises), and the note that the equipment index documents the shipped catalog only — bundled ids live in the adventure that carries them. The "What's not supported" section's closed-loader paragraph names `load_equipment` beside `load_monsters`, so the guide's no-merge-path rule and its new items section agree.
- **`tools/docs/rejection_codes.json`** gains the one-line `items.purchase.not_stocked` description — the docs drift gate (`test_docs_gates.py`) asserts the scanned `Rejection(code=...)` literals and the description file agree in both directions, so the entry lands with the handler change, and both branches of the split keep their codes as string literals, which the scanner requires.
- **`CHANGELOG.md`** `[Unreleased]` gains the Added bullet: `Adventure.items` and `GameSession.effective_equipment`, the collision rule, the resolution surfaces, the town-shop rule with its `items.purchase.not_stocked` rejection code. No Changed bullet — cache `item_ids` were already validated, so no previously-accepted content tightens — and no Fixed bullet for the `_grant_mundane` crash, which is unreachable until bundles exist. No release work item: phase 10's roadmap entry names no version, and the 1.3.x–1.4.x cadence cuts releases independently of phases; the bullet rides `[Unreleased]` into the next minor.
- **`docs/adaptations.md` gains no entries** — the town-shop pin is a spec reading recorded in the spec itself, not a RAW-ambiguous rules interpretation; recorded here so the register's silence is deliberate.

### 5. Tests — `tests/test_adventure_items.py` (new), following the one-file-per-area convention

- The field: default round-trips; a bundled template of each of the four `item_type`s survives document parse (`model_validate` on the discriminated union) and `save_game` → `load_game` with `session_state` equality; a pre-phase save without the key loads with the default.
- Validation: duplicate bundled ids, an equipment-catalog collision, and a magic-catalog collision each report `ContentValidationError` through the one gate with every colliding id named; a collision plus otherwise-valid cache references reports exactly the collision lines (the total-failure-path pin); a cache naming a bundled id validates; a dangling bundled-ish id still fails; the shipped equipment and magic namespaces are disjoint (pinning the precondition the collision rule stands on); a bundled item with id `"gem"` — a treasure-weight id — validates and resolves through `effective_equipment`, pinning that the weights list is outside the identity namespace.
- The engine: a cache carrying a bundled gear item is taken and the `ItemAcquiredEvent` carries its catalog id — the milestone's "observed"; `GrantItem` grants a bundled id; `GiveItems` hands a bundled stack across (the deleted-resolution path, formerly a crash); a bundled item dropped and retaken round-trips through the pile; `PurchaseEquipment` naming a bundled id rejects `items.purchase.not_stocked` while a genuinely unknown id still rejects `session.command.unknown_item` (the carve-out and its honest split, both pinned); the leftovers path reports a bundled id in `ItemsLeftBehindEvent`.
- Persistence and replay: a session holding bundled items in inventory and in a drop pile saves, loads, and replays to equal state; a doctored save whose adventure bundles a colliding item id fails `load_game` with `ContentValidationError`.
- The effective catalog: an empty bundle returns the cached base catalog object (identity assertion); a non-empty bundle resolves shipped and bundled ids through `effective_equipment`; the property is stable across calls.
- The full gate green: `uv sync && uv run ruff format --check && uv run ruff check && uv run pyright && uv run pytest && uv run mkdocs build --strict`.

## Sequencing

1. Work item 1 (the field) with its persistence tests — the document shape lands first and everything else consumes it.
2. Work item 2 (the helper and validation) — the gate exists before any engine path can reach a bundled id.
3. Work item 3 (the session catalog, the redirects, the town-shop pin) with the engine tests — take, grant, give, retake, purchase-rejection.
4. Work item 4 remainder (docs, the spec sentence, changelog; the full gate on both OSes).

## Definition of done

- `uv sync && uv run ruff format --check && uv run ruff check && uv run pyright && uv run pytest && uv run mkdocs build --strict` green on both OSes.
- A bundled gear item is validated, placed in a cache, taken, granted, given, dropped and retaken, persisted, and replayed, observed by catalog id throughout — pinned by the phase's tests, with the consumer calls `validate_adventure(adventure, load_monsters(), load_equipment())` and `validate_content_pack(pack, load_monsters(), load_equipment())` unchanged.
- Colliding and dangling bundled ids fail the standard validation gate with `ContentValidationError`; the doctored-save path fails typed at `load_game`; a bundled id at the town shop rejects `items.purchase.not_stocked`.
- No `SCHEMA_VERSION` bump, no golden regeneration, no `__all__` change; `test_public_surface.py` passes unedited.
- The spec's town-shop sentence, the docstring sweep, the retitled authoring guide with its items section, and the changelog bullet land with the implementation PR; every deferred item above names its pickup.
